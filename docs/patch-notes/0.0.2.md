# Edonism 0.0.2 — Original street board (work in progress)

- **Issue #5:** The original Edonism board is recreated as an isometric 3D city, replacing the 0.0.1 illustrative hex grid.
- Single canonical data file `src/shared/board/edonism-board.v1.json`: 7 streets, City Hall, 30 activity slots and drawn road regions. Browser and .NET read this same file.
- Read-only API endpoint `GET /api/v1/board` for public board structure.
- Domain street graph validates reachability, reciprocal connections and legal single-street adjacency, independent of 3D coordinates.
- Deterministic seed/version-based shuffle for an **already approved set of 30 activity cards**; full composition of a match's activities and mandatory starting cards is deferred to #6.
- React viewer: select 7 streets and 30 lots, inspect adjacent roads, themes and Italian/English text; DOM controls are keyboard accessible and work without WebGL.
- xUnit adjacency/graph/placement regression tests; Playwright on board selection, neighborhood, responsive, themes and i18n.
- Placeholder buildings and Pucciottini are generated by Three.js; no permanent art or live gameplay is included.

**Verification:** CI on PR #11: .NET 10 Release build with 28/28 xUnit tests (including API contract tests), frontend typecheck/bundle and 5/5 Playwright flows.

**Limits:** connections inferred from the original board image are documented for review. This milestone does not move players, grant ownership or implement the game engine. Rules source and deck assets are not published in the repository.

- Aggregato in Domain per match preconfigurati da sorgente fidata: posizione iniziale da ActivitySlotId, 4 atoms, 2 token Diplomazia e 16 scagnozzi totali per giocatore; nessuna carta/fazione inventata.
- Comandi server-authoritative per un singolo movimento gratuito verso una strada adiacente e per la fine del turno; revisioni ottimistiche e cronologia di eventi con identificativo dell'attore.
- L'ultimo turno ferma la partita su `AwaitingRoundSettlement` in attesa delle fasi stipendio/rifornimento/elezioni da sviluppare in #6; la rotazione del turno successivo è calcolabile ma non ancora eseguita.
- Prototipo API **solo Development** (`/api/dev/matches`) con capability token segreto per posto, store in memoria con lock sulle operazioni; nessun comando di partita esposto in Production. Login, persistenza e sicurezza multiplayer sono tracciati in #13.
- Test xUnit di regole e integrazione delle API; la scena 3D rimane un'esplorazione statica (non promette una partita completa).

## Attività iniziali e salario lordo (#14, verificata)

- Una attività iniziale è ora controllata dal proprietario del fixture server-side, con **uno scagnozzo in piedi** e 15 scagnozzi ancora disponibili, come da `rulebook2` p. 4.
- Una funzione Domain pura calcola **solo il salario lordo**: 2 atoms base + un atom per attività posseduta e presidiata da scagnozzo in piedi; scagnozzi atterrati esclusi (p. 5). Espone quote read-only nello snapshot di match.
- Nessun accredito automatico, imposta, vantaggio `Innovate` o modifica di ownership da parte del client; `AwaitingRoundSettlement` resta la barriera fino alle decisioni #4/R-08 e al completamento #6.
- Nuovi test xUnit su controllo iniziale, conteggi e validità delle riserve, duplicati, proprietari inesistenti, scagnozzi atterrati, immutabilità ed endpoint Development. Playwright di regressione invariati.
